# 字幕マッチングの公開化と拡張機能の管理者用/一般用分離

GitHub Issue: #632

## 概要

字幕フィンガープリントによる楽曲推測（照合）を登録ユーザー以外にも開放し、あわせてブラウザ拡張を「一般用（閲覧・照合系）」と「管理者用（データ収集・書き込み系）」に分離するための具体化設計。Issue #632 はアイデア段階の構想メモであるため、本ドキュメントは実装計画そのものではなく、構想を実装可能な粒度まで落とし込み、フェーズ分割と判断ポイントを明確にすることを目的とする。

## 背景・目的

- 字幕フィンガープリント照合（`SubtitleMatchingService`）は正規化・楽曲マスタに依存せず、フィンガープリント同士のJaccard比較のみで動作する。現状はSanctumトークン＋admin認証（＝全登録ユーザー）でしか使えない
- 実測（2026-08-16時点、FP 3,873件・4チャンネル）で、異チャンネル間でも同一曲の類似度がほぼ劣化しない（現しきい値0.15以上が88%）ことが確認された。参照プールはチャンネルを超えて転用可能であり、プールが育つほど新規チャンネルでも候補が出るネットワーク効果が期待できる
- 拡張機能にはYouTube的にグレーな領域（チャットリプレイの内部API取得、`page-bridge.js`によるfetch/XHR傍受）が含まれ、かつ単一の`content.js`（約7,900行）に全機能が同居しており、一般配布可能な品質・リスク水準にない

## スコープ

### 対象

- 公開照合API（読み取り開放）の設計
- 拡張機能の一般用/管理者用の分離方式の設計
- 一般開放後のデータ集積（字幕送信・タイムスタンプコメント回収）の設計
- フェーズ分割と各フェーズの判断ポイント・未決事項の整理

### 対象外

- 実装（各フェーズの実装Issueは着手判断後に別途起票する）
- 歌いだし位置の自動検出（#547）
- 楽曲マスタ・正規化マッピングの公開編集
- サイト本編UIの一般向け照合フォーム（未決事項として記載）

## 現状整理（実装ベース）

具体化の前提となる現行実装の事実関係。

### 照合パイプライン

- フィンガープリント生成: `SubtitleFingerprintService`
  - 60秒窓（`WINDOW_DURATION_SEC = 60`、リード1秒）、文字トライグラム、最小20トライグラム
  - **表示中の**タイムスタンプ（`ts_items.is_display = '1'`）からのみ生成。非表示化されたts_itemのFPは再生成時に削除される（＝サイト本編のキュレーションがそのままプール品質管理になっている）
- 照合: `SubtitleMatchingService`
  - Jaccard類似度、しきい値 `DEFAULT_THRESHOLD = 0.15`
  - 同チャンネル優先で検索し、3件未満のとき全チャンネルへフォールバック（`MIN_CHANNEL_CANDIDATES = 3`）
  - `getCandidateSongsForPosition(videoId, sec)` は保存済み字幕から窓を切り出してオンザフライで照合（#595で一般化済み）
  - 検索は `chunkById(500)` による**PHP内フルスキャン**（SQL側の絞り込みは `duration_sec` 一致のみ）

### 認証・書き込み経路

- 全APIは `auth:sanctum` + `admin` ミドルウェア＋ルート個別throttle。`admin` は実質「登録ユーザーであること」のチェック（`User::isAdmin()` は常にtrue）なので、Issueの「書き込みは登録ユーザーのみ」は現行の認証構成と一致する
- プールへの書き込み経路は `POST api/manage/archives/subtitles/store`（`SubtitleApiController@store`）のみ。照合系エンドポイント（`matchByPosition`/`matchCandidates`）は読み取り専用

### 拡張機能の機能マップ

| 機能 | 実装箇所（主要） | 性質 |
|---|---|---|
| 音量グラフ・スキャン | `content.js` + `background.js`(tabCapture) + `offscreen.js` | クリーン（標準API） |
| タイムスタンプエディタ・コピー | `content.js`（マーカー、undo/redo、`copyTimestamps`） | クリーン |
| 曲名候補表示 | `content.js`（`showSongCandidates` → `GET api/extension/subtitle-matches`） | 読み取り系（要トークン） |
| 字幕取得・送信 | `content.js`（timedtext取得 → `postSubtitlesToServer`）＋ `page-bridge.js` のfetch傍受 | 書き込み系・傍受はグレー寄り |
| リストスキャン/字幕一括取得 | `content.js`（`scan-targets`/`subtitle-targets` API） | 書き込み系 |
| チャットリプレイ取得・検索 | `content.js`（`youtubei/v1/live_chat/get_live_chat_replay` 直叩き）＋ `page-bridge.js` | **グレー（内部API）** |
| ハイライト検出 | `content.js` → `api/extension/highlights/detect`（Claude API） | 管理者向け |
| manage画面連携 | `content-ycs.js` | 管理者向け |
| チャット遅延・Google AI非表示 | `content-chat-delay.js` / `content-google.js` | 独立機能 |

## 設計

### 1. 公開照合API（読み取り開放）— Phase 1

#### 1.1 エンドポイント

```
POST /api/public/subtitle-matches   （認証なし・匿名可）
```

- リクエスト: `{ "subtitle_text": "<60秒窓相当の字幕テキスト>", "duration_sec": 60 }`
  - **生テキストを受け取り、正規化・トライグラム化はサーバー側で行う**。`normalizeForFingerprint()` / `generateTrigrams()` のロジックはバージョン更新があり得るため、クライアントにトライグラム化を持たせると整合が壊れる
  - 窓の切り出し（再生位置±の範囲選択）はクライアント責務。サーバーは受け取ったテキストをそのまま1つの窓として扱う
- レスポンス: `{ "has_fingerprint": bool, "candidates": [...] }`
  - `has_fingerprint = false` はトライグラム20未満（既存の `MIN_TRIGRAM_COUNT` と同義）
- バリデーション: `subtitle_text` の最大長（例: 10,000文字。60秒窓の実測上限から余裕を持たせて決める）、`duration_sec` は当面60固定

#### 1.2 サービス層の変更

`SubtitleMatchingService` に、トライグラム配列を直接受け取る公開用メソッドを追加する（#595 の一般化の延長）。

```php
public function getCandidateSongsForTrigrams(
    array $trigrams,
    int $durationSec = 60,
    float $threshold = self::DEFAULT_THRESHOLD
): array
```

- チャンネルコンテキストが無いため、同チャンネル優先ロジック（`MIN_CHANNEL_CANDIDATES`）は通らず、常に全チャンネル検索（`findSimilarOtherChannels` 相当を除外なしで実行）
- 既存の `getCandidateSongs` / `getCandidateSongsForPosition` は挙動不変

#### 1.3 プール非汚染の境界（最重要の設計原則）

- **公開APIは read-only**。`video_subtitles` / `subtitle_fingerprints` への書き込みコードパスを一切持たない
- 書き込みは既存の認証付き `store` エンドポイントのみ。境界はコントローラ層で保たれる（`SubtitleMatchingService` は現状も書き込みを持たないため、サービス層の変更は安全）
- 公開APIに投げられた字幕テキストは**保存しない**（ログにも本文は残さない）。将来「未キュレーションプール」を作る場合も、明示的な送信エンドポイント（Phase 3）経由に限定する

#### 1.4 レスポンス項目の絞り込み

既存 `rankCandidates()` の出力から、匿名向けには内部情報を落とす。

- 返す: `song_id`, `song_title`, `song_artist`, `text`, `similarity`, `match_count`
- 返さない: `matches[]`（ts_item_id・video_id等の内部詳細）, `source`, `normalized_text`
- タイムスタンプ・曲名はサイト上で公開済みの情報だが、内部IDの列挙面を匿名に晒す必要はない

#### 1.5 認証・クォータ・荒らし対策

段階的に強化する前提で、Phase 1 は throttle のみで開始する。

- IPベース throttle: 例 `throttle:10,1`（10回/分）＋ 日次上限（`RateLimiter` のカスタム定義で 例 200回/日/IP）
- ペイロード上限: バリデーション＋ `LimitRequestBody`（Webサーバー側）
- 異常検知は既存の `api/user-actions/log` 相当のアクセスログ集計で運用開始し、匿名APIキー発行（登録不要のキー配布 or 拡張同梱キー）は**荒らしが実際に観測されてから**導入を検討する（未決事項#4）
- CORS: 一般用拡張は `host_permissions` で呼ぶためCORS制限は防御にならない。Origin制限には頼らない

#### 1.6 性能とスケール限界

現状の照合はFP全件のPHP内フルスキャンであり、公開化のボトルネックになる。

- 現状規模（約4,000件）では1リクエストあたり実用範囲だが、「プール成長 × 公開リクエスト数」の積で悪化する
- Phase 1 公開前に負荷試験を行い、「FP件数 N × リクエスト/分 R」の許容ラインを実測して記録する
- 改善候補（必要になった時点で別Issue化）:
  1. トライグラム転置インデックステーブル（`trigram` → `fingerprint_id`）による候補の事前絞り込み
  2. 同一入力に対する結果キャッシュ（入力テキストのハッシュキー、短TTL）
  3. MinHash/LSH による近似絞り込み（プールが数十万件級になった場合）

### 2. 拡張機能の分離 — Phase 2

#### 2.1 分離方式の比較と推奨

| 方式 | 内容 | 評価 |
|---|---|---|
| A: 別拡張2本 | リポジトリ内で別ディレクトリの2拡張 | コード重複が発生し保守が二重化する |
| B: 単一拡張でトークン有無により出し分け | 実行時に機能をゲート | **不可**。グレー機能のコードが一般配布パッケージに同梱される。ストア審査・規約リスクが残り、分離の目的を達成しない |
| C: 単一コードベース＋ビルドで2成果物 | 共有モジュール＋エディション別manifest/エントリ | **推奨**。一般用パッケージにはグレー機能のコード自体が含まれない |

方式Cを推奨する。一般用の成果物には、チャットリプレイ取得・fetch傍受・スキャン系のコードが物理的に含まれないことを分離の完了条件とする。

#### 2.2 前提リファクタ（Phase 2の大半はこれ）

`content.js`（約7,900行）のモノリスをビルド分離可能な機能モジュールに分割する。

- 分割単位は「2.3 機能振り分け表」の行に対応させる（音量グラフ、タイムスタンプエディタ、候補表示、字幕送信、スキャン、チャット検索、ハイライト検出）
- ビルドツール（esbuild等）を導入し、`manifest.admin.json` / `manifest.general.json` からそれぞれのエントリを束ねる
- このリファクタは挙動不変で先行実施できるため、独立Issueとして切り出す（#556 の手動確認チェックリストを回帰確認に使う）

#### 2.3 機能振り分け表

| 機能 | 一般用 | 管理者用 | 備考 |
|---|---|---|---|
| 音量グラフ・直接スキャン | ○ | ○ | tabCapture はユーザー明示操作で起動するクリーン機能 |
| タイムスタンプエディタ・コピー | ○ | ○ | Phase 3 のコメント回収と接続（コピー＝完成の合図） |
| 曲名候補表示 | ○（公開API・トークン不要） | ○（既存API） | 一般用の照合フローは 2.4 |
| 字幕のサーバー送信 | ×（Phase 3 でオプトイン検討） | ○ | |
| リストスキャン/字幕一括取得 | × | ○ | |
| チャットリプレイ取得・検索 | × | ○ | グレー領域。一般用にはコード自体含めない |
| ハイライト検出 | × | ○ | Claude APIキー前提 |
| manage画面連携（content-ycs.js） | × | ○ | |
| page-bridge のfetch/XHR傍受 | ×（下記） | ○ | 一般用は傍受なしで成立させる |
| チャット遅延・Google AI非表示 | 要判断 | ○ | 照合と無関係な独立機能。一般用に入れるかは未決事項#6 |

#### 2.4 一般用の照合フロー

一般ユーザーはサーバーに字幕を保存できないため、#595 の「サーバー保存済み字幕から窓切り出し」フローは使えない。クライアント完結で窓テキストを作り、公開APIへ送る。

1. マーカーの「候補」ボタン押下
2. 拡張がYouTubeのプレイヤーレスポンスから字幕トラック一覧を取得（`page-bridge.js` の傍受には依存せず、`ytInitialPlayerResponse` / 明示的なtimedtext取得のみで実装。ja手動 > ja自動 > 先頭 の優先は既存 `pickPreferredCaptionTrack` と同一）
3. マーカー秒位置の60秒窓テキストをクライアント側で切り出し（`extractSubtitleWindow` 相当のロジックをJSに移植。正規化はサーバー側なので**窓の切り出しのみ**）
4. `POST /api/public/subtitle-matches` → 候補ポップアップ表示（既存UIを流用）

- 字幕が存在しない動画は「候補なし（字幕がありません）」を1行表示
- timedtextの取得自体は字幕表示という本来機能の範囲であり、チャット内部APIとはリスク水準が異なると整理する（ストア公開時のプライバシーポリシー記載は必要。未決事項#3）

### 3. データ集積（一般開放後の書き込み） — Phase 3

Issue コメント（2026-08-15）の設計案を採用の方向で具体化する。Phase 1/2 とは独立に判断可能で、別プロジェクト級になり得るため、本フェーズは着手判断自体を未決事項とする（未決事項#5）。

#### 3.1 字幕の集積: 未キュレーションプールの隔離

- 一般用拡張からの字幕送信（明示オプトイン）は、既存 `video_subtitles` に**混ぜず**、新テーブル（例: `submitted_subtitles`）に隔離する
- カラム構成は `video_subtitles` 準拠＋送信元識別（匿名なのでIPハッシュ等の最小限）＋ `status`（unreviewed / promoted / rejected）
- 照合プール（`subtitle_fingerprints`）への昇格は、対象チャンネル/動画がサイト本編に登録されキュレーション対象になった時点でのみ行う。「入れない境界」はテーブル分離で担保する

#### 3.2 タイムスタンプの集積: コメント回収方式

手入力タイムスタンプの完成品はYouTubeコメントとして公開されるため、拡張から編集中データを送らず、**投稿済みコメントを後から回収**する。

- 一般用拡張: 「この動画にタイムスタンプコメントがある」シグナルのみ送信（`POST /api/public/timestamp-signals`、video_idのみ。throttle強め）
- 新テーブル `comment_harvest_signals`: `video_id`, `signaled_count`, `last_signaled_at`, `harvested_at`, `status`
- サーバー: シグナルのあった動画のみ `commentThreads.list`（1 unit/call）で回収し、既存のコメント→タイムスタンプ抽出パイプラインを流用
- クォータ制御: 日次回収上限（例: 100動画/日）＋同一動画の再回収間隔（例: 7日）。既存のアーカイブ更新クォータと合算で YouTube API 日次10,000 units 内に収める試算を回収上限の根拠とする
- 折衷案（拡張内マーカーの直接送信を「コピー」ボタントリガーで行う）は、コメント回収方式で不足が観測された場合の追加手段とし、Phase 3 初期スコープからは外す

#### 3.3 未登録チャンネルデータの格納

回収したタイムスタンプの格納先は2案あり、オーナー判断が必要（未決事項#2）。

- 案a: 非表示のshadowチャンネルとして `channels`/`archives`/`ts_items` に取り込む（既存パイプライン・照合コードをそのまま流用できるが、本編テーブルに未キュレーションデータが混入する）
- 案b: 別ステージングテーブル群に隔離（境界は明確だが、抽出・正規化・照合の各処理に二重実装が生じる）
- 評価軸: 「3.1 の境界原則（テーブル分離）」と「実装コスト」のトレードオフ。案aを採る場合は `is_display=0` 固定＋FP生成対象外の保証が最低条件

### 4. フェーズ分割と完了条件

| Phase | 内容 | 完了条件 | 依存 |
|---|---|---|---|
| 1 | 公開照合API | 匿名で候補取得可能。書き込みゼロをテストで保証。負荷試験の記録 | なし |
| 2a | 拡張モジュール分割（挙動不変） | ビルドで現行と同等の成果物が出る。#556 チェックリスト合格 | なし |
| 2b | 一般用エディション | 一般用成果物にグレー機能コードが含まれない。トークンなしで候補表示が動く | 1, 2a |
| 3 | データ集積 | 未キュレーション隔離＋コメント回収の稼働。クォータ試算内での運用 | 1（2bがあると効果大） |

各Phaseの実装Issueは着手判断後に個別に起票し、本ドキュメントを親仕様として参照する。

## 未決事項（オーナー判断が必要）

1. **公開APIの提供形態**: 拡張専用か、サイト本編にも匿名照合UI（字幕テキスト貼り付けフォーム等）を出すか
2. **未登録チャンネルデータの格納方式**: shadowチャンネル（案a） vs ステージングテーブル（案b）（3.3）
3. **一般用拡張の配布方法**: Chrome Web Store 公開（審査・プライバシーポリシー・timedtext取得の説明が必要）か、GitHub Releases等での配布か
4. **匿名APIキーの要否**: Phase 1 はIP throttleのみで開始し、荒らし観測後に判断（1.5）
5. **Phase 3 の位置づけ**: 本体機能として進めるか、別プロジェクトとして切り出すか
6. **独立機能（チャット遅延・Google AI非表示）の帰属**: 一般用に含めるか、管理者用のみか、そもそも別拡張か

## リスク

- **プール品質の希薄化**: read/write非対称＋テーブル分離で構造的に防止する（1.3, 3.1）。公開APIに書き込みパスを作らないことをテストで固定する
- **YouTube規約・ストア審査**: 一般用からグレー機能をコードレベルで排除（2.1 方式C）。timedtext取得の扱いは配布方法の判断（未決事項#3）とセットで整理
- **照合の性能限界**: PHP内フルスキャンが律速。公開前の負荷試験と改善候補の準備（1.6）
- **YouTube APIクォータ**: コメント回収はシグナル駆動＋日次上限で制御（3.2）
- **精度の希薄化**: 実測では異チャンネル間でも0.15以上が88%であり読み取り開放自体は精度に影響しない。プールに未キュレーションデータを入れない限り、公開化による精度低下要因はない
