# PR一括レビュー・修正コマンド

指定されたベースブランチに対するオープンPRを順番にレビューし、問題があれば修正してマージ可能な状態にする。

レビューは**レビューエージェント**と**検証エージェント**の2段階で行い、レビューの質と網羅性を担保する。

## 引数

- `$ARGUMENTS`: ベースブランチ名（例: `develop`）、オプションで `--merge` フラグ

## オプション

- `--merge`: レビュー承認後に自動でマージする

## 手順

### 1. PR一覧の取得

```bash
gh pr list --base <ベースブランチ> --state open --json number,title,headRefName,author,url
```

取得したPR一覧をユーザーに提示し、処理対象を確認する。
PRが0件の場合はその旨を報告して終了する。

### 2. 各PRのレビューループ

取得した順番に、各PRに対して以下を実行する。
各PRのレビュー→修正ループの回数を1からカウントし、5回に達したら中断する。

#### 2.1 PRブランチをベースブランチに同期

レビューを始める前にPRのブランチを最新のベースブランチにrebaseする。これは以下の理由から必須:

- 別PRが先にマージされてベースブランチが進んでいると、`gh pr diff` が古いベースとの差分を返し、すでに解消済みの「指摘」を出してしまう
- レビューエージェント・検証エージェントは差分や `git log` を元に判断するため、ベースとの整合性が崩れると誤検出が増える
- マージ時のコンフリクトも先に解消できる

手順:
1. ベースブランチを最新化:
   ```bash
   git checkout <ベースブランチ>
   git pull origin <ベースブランチ>
   ```
2. PRブランチを取得してrebase:
   ```bash
   git fetch origin <branch_name>
   git checkout <branch_name>
   git rebase <ベースブランチ>
   ```
3. **コンフリクトが発生した場合**: 自動解決を試みず、ユーザーに相談する（`git rebase --abort` してから状況を報告）
4. **rebaseが正常完了した場合**: force-with-leaseでpush:
   ```bash
   git push --force-with-lease origin <branch_name>
   ```
   ※ rebaseで履歴が書き換わるため通常のpushは失敗する。`--force-with-lease` は他人の作業を上書きしないので比較的安全
5. **既にベースブランチを含んでおりrebase不要だった場合**: pushはスキップ

ベースブランチがPRブランチに含まれる祖先と一致しているか確認する簡易チェック:
```bash
git merge-base --is-ancestor origin/<ベースブランチ> <branch_name> && echo "同期済み" || echo "要rebase"
```

#### 2.2 PRの情報収集

- `gh pr view <number>` でPRの説明・関連Issueを確認
- `gh pr diff <number>` で差分を取得（rebase後の最新差分）
- 差分だけでは文脈が不足する場合、関連ファイルの全体を読んで理解を深める
- PRに既存のレビューコメントがあれば確認する

#### 2.3 レビューエージェントによるレビュー

**別のエージェント（サブエージェント）を起動して**レビューを実施させる。レビューエージェントには以下を伝える:

- PRの差分（`gh pr diff`の結果）
- PRの説明・関連Issue
- 関連ファイルのパス
- レビュー観点（下記）
- 結果の出力形式（下記のレビューコメント形式）

##### レビュー観点

全ての観点を機械的にチェックするのではなく、PRの内容に応じて重要な観点に注力する。

**機能的正確性**
- 変更がPRの目的（タイトル・説明・関連Issue）を正しく達成しているか
- エッジケースや境界値への対応は十分か
- ロジックに漏れや矛盾がないか

**セキュリティ**
- SQLインジェクション、XSS、CSRFなどの脆弱性
- ユーザー入力のバリデーション・サニタイズ
- 機密情報（APIキー、パスワード等）のハードコーディング
- 認証・認可の適切な実装

**パフォーマンス**
- N+1クエリ問題
- 不要なDB問い合わせやループ内クエリ
- 大量データ処理時のメモリ効率
- 適切なインデックスの利用

**テスト**
- 変更に対応するテストの有無
- テストが意味のあるケースをカバーしているか
- テストが壊れていないか（`php artisan test` で確認）

**スコープ適合性**
- 変更がPRの目的の範囲内に収まっているか
- 無関係なリファクタリングや修正が混入していないか

**コードスタイル**
- プロジェクトのフォーマッター（Laravel Pint等）に準拠しているか
- 命名規則の一貫性
- 不要なコメントや未使用のコードがないか

**互換性・影響範囲**
- 既存機能への影響・破壊的変更
- マイグレーションの安全性（本番データへの影響）
- 依存関係の変更による影響

##### 修正方針

レビューエージェントは、致命的な問題だけでなく「修正した方がよい」改善点も全て指摘する。具体的には:

- **必須修正**: バグ、セキュリティ脆弱性、データ不整合など放置できない問題
- **推奨修正**: 可読性の改善、命名の統一、不要コードの除去、より適切なパターンの採用など、コード品質を高める改善

どちらも指摘事項として報告し、全て修正対象とする。

#### 2.4 検証エージェントによるレビュー結果の検証

レビューエージェントの結果を受け取ったら、**別のエージェント（サブエージェント）を起動して**レビュー結果の検証を行わせる。検証エージェントにはレビュー結果を渡した上で、独立した視点から検証させる。別エージェントが改めて確認することで、レビューの質を担保する。

検証エージェントには以下を伝える:

- レビューエージェントの指摘事項一覧
- PRの差分（`gh pr diff`の結果）
- PRの説明・関連Issue
- 関連ファイルのパス
- 検証観点（下記）

##### 検証の観点

**指摘の妥当性検証**
- レビューエージェントの各指摘が技術的に正しいか、実際のコードを読んで確認する
- 誤検出（問題ないのに問題とされている箇所）がないか確認する
- 指摘の重要度（必須/推奨）が適切か確認する

**影響範囲の調査**
- 指摘箇所に関連するコードをGrepで検索し、影響範囲を特定する
- 変更によって呼び出し元・参照元に不整合が生じていないか確認する

**類似パターンの横断チェック**
- 指摘された問題と同様のパターンがコードベースの他の箇所に存在しないかGrepで確認する
- 同じ修正が必要な箇所があれば報告する

**見落としチェック**
- レビューエージェントが見落としている問題がないか、独自にPRの差分を確認する
- レビュー観点に沿って、追加で指摘すべき点がないか確認する

**テスト・ビルドの実行**
- `php artisan test` を実行してテストが通ることを確認する
- コードスタイルチェック（`./vendor/bin/pint --test`）を実行する

#### 2.5 レビュー結果の統合と判定

レビューエージェントと検証エージェントの結果を統合する。

- 検証エージェントが「誤検出」と判定した指摘は除外する
- 検証エージェントが追加で発見した指摘をマージする
- 類似パターンの横断チェックで見つかった追加修正箇所を含める
- 指摘が矛盾する場合は、コードを実際に確認して正しい方を採用する
- 統合結果に基づいて最終判定（承認 or 要修正）を下す

#### 2.6 レビュー結果に応じた対応

**問題なし（承認）の場合:**

修正が一度も行われていない場合（初回レビューで承認）:
→ 2.8 最終承認に進む（2.7 ユーザー確認はスキップ）

修正を経て承認になった場合:
→ 2.7 ユーザー確認に進む

**問題あり（要修正）の場合:**

1. GitHubにrequest-changesレビューを投稿する:
   ```bash
   gh pr review <number> --request-changes --body "レビューコメント"
   ```

   レビューコメントは以下の形式で記載する:

   ```
   ## レビュー結果: 要修正

   ### 概要
   [変更内容の要約と全体的な評価]

   ### 指摘事項
   - **[必須/推奨]** `ファイル名:行番号` - 指摘内容と修正方針

   ### スコープ外の問題（該当がある場合）
   - 問題内容 → Issue #XXX として作成済み

   ### 良い点
   [コードの良い点があれば記載]
   ```

2. PRのブランチをチェックアウトする:
   ```bash
   git fetch origin <branch_name>
   git checkout <branch_name>
   ```

3. 指摘事項を**全て**修正する（必須・推奨の両方）
   - 修正内容がPRのスコープ内であることを確認
   - 類似パターンの横断チェックで見つかった箇所も修正する
   - テストがある場合は `php artisan test` で確認
   - コードスタイルは `./vendor/bin/pint` で整形

4. コミット・プッシュする:
   ```bash
   git add <修正ファイル>
   git commit -m "修正内容の説明"
   git push origin <branch_name>
   ```

5. 修正内容をPRにコメントする:
   ```bash
   gh pr comment <number> --body "修正内容の説明"
   ```

6. 2.3に戻って再度レビュー・検証ループを実行する（問題がなくなるまで繰り返す）

**ループ上限（5回）に達した場合:**

レビュー→修正→再レビューのループが5回に達しても収束しない（新たな指摘が出続ける）場合、そのPRの処理を中断する。

1. PRにコメントを投稿し、状況を記録する:
   ```bash
   gh pr comment <number> --body "自動レビュー・修正ループが5回に達しましたが収束しませんでした。残存する指摘事項をまとめます。以降の対応はユーザーの判断に委ねます。

   ### 残存する指摘事項
   - [未解決の指摘を列挙]

   ### これまでの修正履歴
   - [各ループで行った修正の概要]"
   ```
2. このPRをスキップし、次のPRの処理に移る
3. サマリー報告で「ループ上限到達」として報告する

**スコープ外の問題を発見した場合:**

- PRへの指摘としては扱わない
- GitHubにIssueを作成する:
  ```bash
  gh issue create --title "タイトル" --body "問題の説明"
  ```
- 類似のIssueが既にあれば、そのIssueにコメントを追記する
- PRのレビューコメント内で「スコープ外の問題」セクションにIssue番号を記載する

#### 2.7 ユーザー確認

修正を行った場合、変更内容をユーザーに提示して確認を求める。
ユーザーから指摘があれば修正し、再度確認する。
指摘がなくなるまで繰り返す。

#### 2.8 最終承認

全ての指摘が解消され、ユーザー確認も完了したら:

1. GitHubにapproveレビューを投稿する:
   ```bash
   gh pr review <number> --approve --body "レビューコメント"
   ```

   承認コメントは以下の形式で記載する:

   ```
   ## レビュー結果: 承認

   ### 概要
   [変更内容の要約と全体的な評価]

   ### 確認した観点
   - [確認した主要な観点を列挙]

   ### 良い点
   [コードの良い点があれば記載]
   ```

#### 2.9 マージまたは次のPRへの移行

**`--merge` 指定時:**

1. CIチェックのステータスを確認する:
   ```bash
   gh pr checks <number>
   ```
2. 問題なければマージする:
   ```bash
   gh pr merge <number> --merge --delete-branch
   ```
3. ローカルをベースブランチに戻す:
   ```bash
   git checkout <ベースブランチ>
   git pull origin <ベースブランチ>
   ```

**`--merge` なしの場合:**

次のPRに移る前にgitの状態を綺麗にする:

```bash
git checkout <ベースブランチ>
git branch -D <処理したPRのブランチ名>  # ローカルのみ削除
```

未コミットの変更が残っていないことを確認してから次のPRに移る。

### 3. サマリー報告

全PRの処理が完了したら、以下をまとめて報告する:

- レビューしたPR数
- 承認したPR数
- 修正を行ったPR数（修正内容の概要も含む）
- マージしたPR数（`--merge` 有効時）
- ループ上限到達で中断したPR数（該当PRの番号・タイトル・残存指摘の概要）
- 作成したIssue数とその内容（スコープ外の問題があった場合）

## 留意点

- レビューで発見された問題がPRの範囲外の場合は、PRへの指摘ではなくIssueを追加して対応する（類似のIssueがある場合はそのIssueに追記）
- 各PR間でgitの状態を綺麗に保つこと（未コミットの変更を残さない）
- マージコンフリクトが発生した場合は、ユーザーに相談する
- 修正は致命的な問題だけでなく、改善できるものは全て対応する
